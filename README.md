# MystiaRecommendation — 东方夜雀食堂稀客推荐插件

一个基于 **BepInEx 6 IL2CPP** 的《东方夜雀食堂》插件。稀客点单后，插件会实时读取当前存档拥有的料理、酒水、厨具、食材库存与流行趋势，计算并显示两套具有不同经营目的的套餐（料理 + 酒水 + 可选附加食材 + 厨具）：**最高消费方案**用于快速清座，**最低消费方案**用于增加进食轮次、获取符卡和刷好感度。这套双策略选择是本插件的核心特色。

## 快速安装

1. 确保游戏已安装 **BepInEx 6 IL2CPP**（[下载](https://builds.bepis.io/projects/bepinex_be)）。
2. 从 [Releases](https://github.com/bbluesky123/MystiaRecommendation/releases) 下载最新的 `MystiaRecommendation-v*.zip`，无需自行编译源码。
3. 在 `<游戏目录>\BepInEx\plugins\` 下创建 `MystiaRecommendation` 文件夹，把 ZIP 的内容解压到该文件夹。
4. 确认最终目录如下，然后启动游戏：

```text
BepInEx/
└── plugins/
    └── MystiaRecommendation/
        ├── MystiaRecommendation.dll
        └── Data/
            ├── customers_rare.json
            ├── recipes.json
            ├── beverages.json
            ├── ingredients.json
            └── area_unlock_schedule.json
```

进入营业后，插件会在稀客出现和完成点单时自动工作。如果推荐状态未及时更新，可按 F5 手动刷新。

## 热键

| 热键 | 功能 |
|------|------|
| F2 | 开关推荐卡片叠加显示 |
| F5 | 重新读取状态并刷新当前活跃稀客的推荐内容；保留卡片位置和折叠状态 |

当前源码没有实现 F1 游戏内配置面板。配置由 BepInEx 自动生成的配置文件管理。

## 当前功能

- **自动识别稀客和多轮点单**：监听稀客姓名、订单生成、食物需求和酒水需求；同一轮重复回调不会重复计算。
- **多稀客支持**：按座位独立维护推荐卡片；客人付款、离座、座位换客或场景切换时自动清理。
- **运行时状态快照**：每份完整订单都会重新读取存档实际拥有的料理、酒水、食材库存和流行趋势，并从营业场景的厨具控制器读取本轮实际携带、放置的厨具；不会把仓库永久拥有但本轮未携带的厨具用于推荐。
- **兼容旧版本解锁判断**：运行时料理所有权接口不可用时，才根据初始、羁绊、玩家等级、任务、商店、特殊来源和区域开放日程进行兜底判断。
- **普通方案追加食材提分**：料理本身先满足稀客点单的食物 Tag，酒水也满足酒水 Tag；随后可从当前实际有库存的食材中添加不冲突的食材，用来补充稀客的其他喜好 Tag、提高方案分数。这里不要求食材库存达到 10 个。
- **食材补订单 Tag（分支 C）**：如果酒水能够满足订单，但料理本身没有稀客要求的食物 Tag，插件会检查是否存在带该需求 Tag 且库存不少于 10 个的食材。若存在，则选择其中库存最多的合格食材，作为额外食材加入本身不带该需求 Tag 的料理，使最终成品满足订单。该路径也会遵守厨具、预算、负面 Tag 冲突、额外食材配置上限和总食材不超过 5 个等限制。
- **夜雀厨具兜底**：正常标签匹配不可行时，如果持有夜雀厨具，会生成放宽订单标签限制的兜底方案。
- **流行趋势**：可把当前流行喜爱/厌恶作为套餐标签参与不同稀客的评分。
- **双经营策略**：先过滤不能满足订单、评分或负面标签要求的组合，再分别选择最高消费与最低消费方案；两者服务于完全不同的经营目标，而不是简单取评分最高的前两名。
- **任务固定料理（方案 D）**：识别稀客头顶感叹号对应的营业任务，从任务状态读取固定料理；固定料理不可替换，只能通过附加食材、标签覆盖和对应夜雀厨具满足订单。额外食材同时受配置上限和总食材不超过 5 个的硬限制。当前无法达到 4 分时仍会显示固定料理的基础食材和厨具，并取消高价/低价拆分，只给出当前可实现的唯一最高分料理与酒水组合；缺少订单 Tag 时会同时提示理论分和预计结算分。
- **分区状态 UI**：尚未确认的完整方案统一进入右上角决策区并按实际高度自上而下排布；识别到玩家实际制作的方案后，自动切换为对应桌边的紧凑执行卡片。
- **交互与多轮提示**：未与稀客对话时在桌子右侧显示“请对话获取需求”；料理和酒水上齐后在桌子左侧显示“等待下一轮”，不再用空白桌边区表达多个不同状态。
- **稀客料理座位标记**：制作中的稀客料理显示对应座位号，取出后根据游戏实际返回的托盘槽位继续显示；插件只记录最多四种可能的槽位坐标，不会假定玩家已解锁四槽，未开放或没有料理的槽位不会绘制标记。
- **可交互卡片**：最多显示 12 位活跃稀客，每张卡片可拖拽；F5 只更新同一状态下的内容，不重置玩家手动位置。卡片跨越决策区和桌边区时会回到新状态的默认位置。
- **未知稀客兜底**：数据表未收录的姓名仍可按本轮食物和酒水订单标签生成基础方案。

> “库存不少于 10 个”只适用于上述分支 C，是插件为该分支设置的候选门槛，并不是游戏自带的保底机制。即使已有料理能直接命中订单 Tag，分支 C 的候选仍会作为补充方案参与后续评分和价格筛选；普通方案中用于增加其他喜好 Tag 的额外食材不受这个 10 个库存门槛限制。任务固定料理则采用独立逻辑：料理不可更换，可先尝试用额外食材补订单 Tag，再尝试对应夜雀厨具；仍无法满足时显示当前最高分方案。

## 核心亮点：双经营策略

本插件不会只给出一个抽象的“最优解”，也不会简单返回评分最高的前两个组合。在筛出能够满足当前订单、预算、厨具、库存和评分要求的候选后，插件会针对实际游玩目标同时给出两个价格极值方案。

### 最高消费方案：快速清座

适用于不需要继续刷该稀客的羁绊，或者该稀客的正面符卡并不重要的情况。

插件会先保证方案达到当前可用的评分要求、不会因为错误标签吃到惩罚符卡，再在这些安全候选中选择账面价格最高的料理与酒水组合。更高的单轮消费可以更快消耗稀客预算，使其减少后续进食轮次并尽快离开座位，把座位腾给新的客人。

这一策略追求的是：

```text
不吃惩罚符卡 + 不强求正面符卡 + 尽可能高的单轮消费 + 更快释放座位
```

### 最低消费方案：多轮进食与刷好感

适用于希望获得稀客正面符卡效果，同时希望让该稀客多吃几轮来提高好感度的情况。

在同样满足订单和评分要求的候选中，插件选择账面价格最低、附加食材成本更低的组合。较低的单轮消费可以让稀客的预算支撑更多轮点单，从而增加进食、好感度积累以及触发正面符卡的机会。

这一策略追求的是：

```text
满足高评分 + 尽可能低的单轮消费 + 更多进食轮次 + 更多好感与正面符卡机会
```

两套方案仍按“最高消费在前、最低消费在后”的固定顺序显示，但 UI 标题不额外添加策略字样，以减少卡片占用空间。它们没有绝对的优劣，选择哪一套取决于玩家此刻更需要座位周转，还是需要培养该稀客。

## 方案 D：稀客好感度任务的固定料理推荐

当稀客头顶出现感叹号时，通常表示该稀客当前带有需要在营业中完成的好感度任务。这类任务与普通点单最大的区别是：**任务要求的料理已经固定，玩家不能用其他料理替代**。如果仍按普通推荐方式在全部料理中选择，即使评分很高，也无法完成这项任务。

方案 D 会读取游戏当前的营业任务状态和任务指定料理 ID，锁定这道固定料理，再围绕它计算可执行方案：

```text
检测稀客营业任务
  → 读取任务指定的固定料理
  → 固定料理本身满足所需食物 Tag？
      ├─ 是：补充其他正面标签，使最终评分达到要求
      └─ 否：加入附加食材补出所需 Tag，并继续提高评分
  → 应用料理负面标签和标签覆盖规则
  → 正常方案不可行时，尝试该料理对应类型的夜雀厨具
  → 在合格结果中继续给出最高消费与最低消费两种策略
```

方案 D 始终遵守以下约束：

- 固定料理不可替换为其他料理。
- 固定料理必须是当前存档实际持有的料理，基础食材也必须有库存。
- 额外食材数量不能超过插件配置的“最大额外食材数”。
- 基础食材与额外食材合计不能超过游戏底层的 5 个食材上限。
- 附加食材必须满足料理负面标签、顾客负面标签和标签覆盖规则。
- 夜雀厨具必须与固定料理需要的厨具类型对应，例如煮锅料理只能使用夜雀煮锅兜底。
- 推荐仍以满足订单和达到目标评分为前提；无法得到合格组合时会明确显示无可用方案，不会偷偷替换任务料理。

方案 D 的目的不是单纯追求价格或评分，而是首先保证任务指定料理能够正确交付，从而帮助玩家完成稀客的好感度任务。在这个前提下，玩家仍可根据需要选择：

- **任务D / 最高消费**：完成固定料理任务的同时尽快消耗预算、释放座位。
- **任务D / 最低消费**：完成固定料理任务的同时控制单轮消费，为后续进食和好感度培养保留空间。

UI 会使用 `任务D` 标识这类推荐，避免与普通自由选菜方案混淆；两套结果仍保持最高消费在前、最低消费在后的顺序。

## 推荐流程

```text
稀客出现
  → 尚未对话：桌子右侧显示“请对话获取需求”
  → 完成对话并取得完整需求：右上角显示完整方案卡片
  → 收集食物标签、酒水标签和订单预算
  → 捕获当前存档的料理/酒水/厨具/食材/流行趋势快照
  → 如果存在感叹号营业任务，锁定任务指定料理并进入方案 D
  → 否则生成正常匹配、食材扩展或夜雀兜底候选
  → 按 4 → 3 → 2 → 1 的最低评分依次降级
  → 必要时添加附加食材提高评分或补齐订单标签
  → 在达标候选中分别显示最高消费和最低消费方案
  → 识别玩家实际开始制作的方案：完整卡片切换为桌子左侧紧凑卡片
  → 料理和酒水上齐：显示“等待下一轮”，直到新需求或稀客离场
```

套餐评分为：

```text
命中的顾客正面标签数 - 命中的顾客负面标签数
```

顾客的酒水偏好标签也会加入正面标签集合。标签冲突时按游戏机制处理“大份覆盖小巧”“灼热覆盖凉爽”“肉覆盖素”“重油覆盖清淡”“饱腹覆盖下酒”。

附加食材价格单独记录；界面中的账面总价和订单预算判断使用料理价格 + 酒水价格。

## 配置

首次运行后，BepInEx 会生成插件配置文件。当前源码实际使用的配置项如下：

| 配置项 | 默认值 | 作用 |
|-------|--------|------|
| 启用叠加显示 | `true` | 推荐卡片总开关 |
| 透明度 | `0.85` | 卡片背景透明度 |
| 字体大小 | `14` | 卡片字体大小 |
| 显示位置 | `OverCustomer` | 旧版本兼容项；当前固定使用“右上角决策区 + 桌边状态区”布局 |
| 考虑流行趋势 | `true` | 是否读取流行喜爱/厌恶并参与评分 |
| 最大额外食材数 | `3` | 补标签或提高评分时最多添加的食材数；总食材仍不超过 5 个 |
| 切换显示 | `F2` | 叠加显示热键 |
| 刷新 | `F5` | 清除缓存并刷新推荐的热键 |

`显示位置` 为旧版本兼容项，当前布局不会根据这个值改变。源码还定义了自动隐藏延迟、优先夜雀厨具、显示标签、显示符卡和显示羁绊等配置项，但当前版本尚未把它们完整接入推荐或 UI；修改这些配置暂时不会产生预期效果。

如果区域开放日程不准确，可直接编辑 `Data/area_unlock_schedule.json` 中的 `absoluteDay`，无需重新编译。

## 料理解锁检测

| 解锁类型 | 当前检测方法 | 说明 |
|---------|-------------|------|
| Self | 直接判定 | 初始自带料理始终可用 |
| Bond | `RunTimeAlbum.GetCharacterKizuna(Int32, out ..., out ...)` | 检查角色区域、羁绊等级以及经验已满但尚未升级的边界状态 |
| LevelUp | `RunTimePlayerData.Level` 或 `RunTimeStorage.HaveRecipe(Int32)` | 无区域限制时比较玩家等级；带区域限制时先检查区域，再查询游戏存档 |
| QuestOrEvent | `RunTimeStorage.HaveRecipe(Int32)` | 先过滤尚未开放的任务区域 |
| Shop / Special / Unknown | `RunTimeStorage.HaveRecipe(Int32)` | 直接以游戏存档为准 |

默认区域日程包括妖怪兽道（day 1）、人间之里（day 17）、博丽神社（day 34）、红魔馆（day 48）和迷途竹林（day 69）。实际完整列表以 `Data/area_unlock_schedule.json` 为准。

每份完整订单都会捕获新的运行时状态快照；同一位稀客当前已经显示的推荐可按 F5 立即重新读取并计算。刷新采用同一卡片就地更新，会保留原订单预算、任务固定料理、屏幕坐标以及各区块的折叠状态。

`recipes.json` 顶层 `id` 对应成品 Food ID。插件从 `RunTimeStorage.GetAllRecipes()` 返回的已拥有 `Recipe` 对象直接读取 `foodID`，再映射到料理名称；`recipeId` 对应游戏 `Recipe.id`，仅用于旧版本 `HaveRecipe()` 的兼容兜底。营业任务返回的也是 Food ID。两套 ID 分开使用，避免数值相同但实际对象不同的料理互相误判。

料理的“实惠”和“昂贵”属于价格动态标签：基础价格小于 20 时附加“实惠”，大于 60 时附加“昂贵”，价格恰好为 20 或 60 时均不附加；若两者同时出现，“昂贵”覆盖“实惠”。插件在载入料理数据时统一应用这条规则，使标签展示与推荐评分保持一致。

## 从源码构建

前置条件：

- [.NET 6 SDK](https://dotnet.microsoft.com/download/dotnet/6.0)
- 已正确安装 BepInEx 6 IL2CPP 的游戏目录

```powershell
git clone https://github.com/bbluesky123/MystiaRecommendation.git
cd MystiaRecommendation

# 复制本机配置模板
Copy-Item Directory.Build.user.props.example Directory.Build.user.props
```

打开新生成的 `Directory.Build.user.props`，把 `BepInExDir` 修改为本机实际的 BepInEx 目录：

```xml
<Project>
  <PropertyGroup>
    <BepInExDir>D:\steam\steamapps\common\Touhou Mystia Izakaya\BepInEx</BepInExDir>
  </PropertyGroup>
</Project>
```

`Directory.Build.user.props` 只保存本机路径，已经被 `.gitignore` 忽略，不会上传到 GitHub。

配置完成后执行：

```powershell
dotnet build -c Release
```

也可以不创建本机配置文件，直接通过命令行参数指定路径：

```powershell
dotnet build -c Release -p:BepInExDir="D:\游戏目录\BepInEx"
```

或者使用环境变量：

```powershell
$env:MYSTIA_BEPINEX_DIR = "D:\游戏目录\BepInEx"
dotnet build -c Release
```

构建前，MSBuild 会检查 BepInEx 核心程序集和游戏 IL2CPP 程序集是否存在。构建成功后，DLL 和 `Data/` 会自动复制到：

```text
BepInEx/plugins/MystiaRecommendation/
```

```text
│   ├── recipes.json                  # 190 个料理及解锁条件
│   ├── beverages.json                # 48 种酒水
│   ├── ingredients.json              # 70 种食材及标签
│   └── area_unlock_schedule.json     # 区域开放日程
```

`GameStateCache.cs` 同时保留早期状态模型和当前推荐使用的运行时快照；`InventoryPatch.cs` 与 `RecipePatch.cs` 是预留结构。当前运行时状态由 `Plugin.cs` 在生成推荐时主动查询，`Load()` 只注册 `CustomerPatch`。

## 开发说明

本项目最初使用 Claude Code 辅助制作。相关本地配置不参与插件运行，也不纳入公开仓库或安装 ZIP。

Release 中的安装 ZIP 包含编译好的 `MystiaRecommendation.dll` 和完整 `Data/` 目录，目的是让其他端或不具备构建环境的使用者可以快速安装。

建议调试时查看 BepInEx 日志中的 `[MystiaRec]` 记录。日志会输出稀客、座位、订单标签、预算、解锁状态、所选推荐分支、候选数量和最终方案。
